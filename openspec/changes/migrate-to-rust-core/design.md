# Design: Migrate to a Rust/Wasm Core (monorepo)

## Technical Approach

Change the data model first, then the language. Phases 1–2 change the data model in TypeScript: a flat RGBA buffer, a `dispatch(cmd)` seam, and dirty-rect history. Phase 3 splits the repo. Phases 4–7 move work behind a `PixelCore` / `PixelKernels` interface into Rust, one piece at a time. A flag picks the implementation, and the TS version stays as the parity reference.

Code facts this design depends on (verified):
- `useSpriteEditorStore` uses zustand `persist` (key `sprite-editor-core`, no `version`) and writes `layers`, `timeline`, canvas size, `activeLayerId` and colors to localStorage as JSON. A `Uint8ClampedArray` does not round-trip through JSON. **Phase 1 moves the document out of zustand persist into IndexedDB (D8, D12).** There is no IndexedDB code in the repo today.
- History stores a snapshot after the action (`pushHistory` runs on pointer-up and in `addFrame`), and `undo` reads from `historyIndex`. The current frame is copied twice: once in `state.layers` and once in `timeline.frames[i].layers`, kept in sync by `save/restoreFrameSnapshot`. **Phase 2 did not actually remove this** — `lib/core/ts-core.ts`'s `DocSnapshot` carried forward the same top-level `layers`/`activeLayerId` fields alongside `timeline.frames[i].layers`, synced only at structural-op boundaries (`syncCurrentFrameIntoTimeline`/`restoreFrame`), which is the same duplication under a new name. **Phase 2b removes it for real**: `DocSnapshot` now holds only `{canvasWidth, canvasHeight, timeline}` — `timeline.frames[currentFrameIndex].layers` is the single mutable copy, and `currentLayers(doc)`/`currentActiveLayerId(doc)` are plain reads of it. The zustand store still exposes top-level `layers`/`activeLayerId` fields (so existing selectors/components are untouched), but they are now a derived cache written ONLY by `core.slice.ts`'s `dispatch` handler, never set directly by another slice.
- These files touch `RgbaColor[][]` and must migrate: `lib/{pixel-buffer,flood-fill,history,quantize,downscale,pixel-transform,image-decode,sprite-pipeline,retro-diffusion-utils,export-utils,canvas-renderer}.ts`, `stores/slices/{pixel,clipboard,selection,compound,history,timeline}.slice.ts`, `stores/types/slices.ts`, `features/canvas/hooks/useCanvasInteraction.hook.ts` (eyedropper `getPixel`), `features/canvas/components/CanvasArea/konva/{SpriteLayers,SelectionOverlay}.tsx` (each has its own `renderPixelsToCanvas` and `getDrawOffset`), `useRightSidebar.hook.ts`, and the tests `quantize`, `downscale` and `stores/index`.
- `sprites/hooks/useCanvasInteraction.hook.ts` and `sprites/hooks/useCanvasRenderer.hook.ts` look orphaned (nothing imports them; the live copies are under `features/canvas/hooks`). Delete them in phase 1, not migrate them.

## Architecture Decisions

| # | Decision | Choice | Alternatives / tradeoff |
|---|----------|--------|-------------------------|
| D1 | Buffer | `{w,h,data:Uint8ClampedArray}`, row-major, `i=(y*w+x)*4` | `Uint32Array` (one write per pixel, but endianness gets in the way of `ImageData`); keep objects (no gain) |
| D2 | Mutation, phase 1 | Copy-on-write: one copy per *batch* | In-place plus a revision counter: breaks the `useMemo` identity that Konva relies on, and is deferred to phase 2 |
| D3 | Ownership, phase 2+ | **Core owns the document** (frames, layer order and metadata, pixels, history). The store holds UI state plus `docRevision` and a read-only `DocSnapshot` | Core owns only pixels: layer and frame undo would then have to span both systems |
| D4 | History | Dirty-rect patches (before/after bytes) plus inverse structural records | COW layer snapshots (O(layer) per step); deep clone (today) |
| D5 | Two seams | `PixelKernels` (stateless, phases 4–6) under `PixelCore` (stateful document, phase 7) | A single seam: the Rust history would have to land first, which is the hardest port |
| D6 | Rust API | Flat methods, `u32` handles, slices plus `rgba: u32`; no serde | `serde-wasm-bindgen` commands: easier to grow, but more crate surface and magic for a Rust newcomer |
| D7 | Memory | Phase 7: buffers live in Wasm memory, and JS reads a *view* that is valid only until the next `dispatch` | Copy out every frame: simpler, but 256 KB/frame at 256² |
| D8 | Persistence (phase 1) | `DocumentRepository` port + **IndexedDB adapter**, drafts stored as native binary (`Uint8Array` per layer, structured clone, no base64). Debounced autosave, restore on load. Zustand persist keeps only UI prefs | base64 in localStorage: +33% size, ~5 MB quota, sync encode on every save, and a second migration in phase 2 |
| D12 | Persistence model (ADR) | **Local-first**: IndexedDB is the working-draft store. Supabase project sync is a later change (`supabase-project-sync`) that adds a 2nd adapter behind the same port | Supabase now: needs auth, conflicts and offline handling; out of scope |
| D13 | IndexedDB access | `idb` (~1.2 KB gz): typed `DBSchema` (no `any` casts on `IDBRequest.result`), promise API, versioned `upgrade` | Raw API: zero deps, but `result` is `any` and we hand-roll promisify + upgrade (~60 LOC of plumbing to maintain) |
| D14 | Phase placement | Persistence lands in **phase 1**, together with the flat buffer | Phase 2: phase 1 would need a throwaway base64 codec, or ship with persistence broken. Phase 2 only swaps the payload source (`core.exportDocument()`); port and adapter stay unchanged |
| D9 | Wasm delivery | Commit `pkg/`; CI rebuilds and diffs it; pin the toolchain and wasm-pack | Rust on Vercel; publish to npm (deferred to 1.0) |
| D10 | TS packages | Source exports (`"exports": "./src/index.ts"`), no tsc build | tsup dist: needed only when publishing |
| D11 | `DESIGN.md` | Stays at the repo root (the agents and CLAUDE.md point there). `packages/tokens` holds `tokens.css` and `colors.ts`, plus a parity test | Move it: breaks the agent contracts. **This deviates from the proposal.** |

### Command Undoability (phase 2c revision — supersedes the phase 2b note below)

**Phase 2c (judgment-day fixes, orchestrator architecture decision, final): patch-based undo is only sound if EVERY document mutation goes through history.** This REPLACES the phase 2b split — every command that mutates DOCUMENT data (pixels, layers, frames) is now undoable. The phase 2b "non-undoable" list below was itself the root cause of two judge-reported bugs (a dangling `activeLayerId` after an un-undoable `layer.remove`, and a patch entry silently corrupted by a later `frame.paste` that it had no way to react to) — leaving any document mutation outside history just relocates the "two sources of truth" problem the Code Facts above describe, it doesn't remove it.

Two families, revised:

- **Undoable** (push a history entry — dirty-rect patch for pixel ops, structural before/after snapshot for layer/frame CRUD): `stroke.begin/points/end`, `fill`, `frame.add`, `frame.remove`, `frame.paste`, `doc.replace`, `layer.add`, `layer.remove`, `layer.meta`, `layer.reorder`, `selection.commit`, `region.clear`, `undo`, `redo`.
- **Non-undoable** (view/playback state — mutate the document, bump `docRevision`, push NO history entry; undoing a document edit must never revert these): `layer.setActive` (which layer is selected), `frame.select` (which frame is being viewed), `timeline.setFps`, `timeline.toggleLoop`, `timeline.setFrameSelection`, `timeline.togglePlayback`.

Supporting fixes that make "everything undoable" actually sound, not just labeled that way:
- History entries address frames by STABLE `frameId`, never array index (`lib/core/history.ts`) — index addressing is exactly what broke under a later structural reorder.
- `applyEntry` never trusts a recorded `activeLayerId` blindly; it falls back to the frame's current id, then its first layer, so undo/redo can never leave `activeLayerId` dangling.
- Structural undo/redo restores `frames`/`currentFrameIndex`/`selectedFrameIndices` but deliberately KEEPS the current `fps`/`loop`/`isPlaying` — those are playback/view prefs, not document data, and reverting them was a second judge-reported bug.
- A stroke is bound to the `frameId`+`layerId` it began on; `stroke.begin`-while-open, `frame.select`, `undo`, `redo` and tool switches all force-commit an open stroke first instead of risking it being silently lost or misapplied.
- `layer.locked` is enforced centrally in the core (not just in the UI) for every pixel-mutating command; bounds are validated on every pixel write (no "wrap to the next row" on an out-of-range coordinate); commands that produce no actual change report `changed:false` and push nothing.

Deviation (documented, time-boxed, not silently dropped): the design's "prefer small structural records over whole-document snapshots where feasible" is NOT implemented for the NEWLY undoable layer/frame ops — `layer.add/remove/meta/reorder` and `frame.paste` reuse the existing whole-timeline `StructuralDocSnapshot` (already correct, already bounded by `pushEntry`'s eviction) instead of bespoke minimal diff records, to keep the judgment-day pass's blast radius contained. Tracked as a follow-up task (see `tasks.md` 2c.4), not re-opened here.

**RESOLVED in phase 2d below** — the deviation above is closed; see "Structural history memory" and "Undo/redo focus".

### Phase 2f (judgment-day round 3 + remaining Wasm-boundary blockers — supersedes nothing above, adds to it)

Two more independent blind judges reviewed phase 2e and reproduced five real bugs in `lib/core/ts-core.ts`, all fixed this round (`tasks.md`'s Phase 2f has the full list and test references). This round also closes two of the four Wasm-boundary blockers the orchestrator flagged (B1, B2) and explicitly documents why the other two (B3, B4) are deferred.

- **Bug fixes, in one line each**: (1) six reducers (`frame.add/remove`, `doc.replace`, `undo`, `redo`, `frame.paste`) rebuilt `CoreState` as a bare object literal instead of spreading the previous state, silently resetting `contentRevision`/`layerRevisions`/`idGenerator` — fixed, and a `withState(prev, patch)` helper now makes that class of bug structurally impossible (every reducer branch goes through it). (2) `frame.paste`/`doc.replace` now validate every incoming buffer's size against the canvas at the command boundary (`changed:false` no-op on mismatch, never resample); `payloadToDoc` skips corrupted layers (falls back to one blank layer per frame, or a whole empty document) instead of crashing on restore; the frame clipboard is cleared when an AI apply actually changes the canvas size. (3) a floating selection is now bound to the `sourceFrameId`/`sourceLayerId` it was lifted from (`SelectionState`), and every action that can change the active layer/frame or the document's structure commits (or cancels) the float into its SOURCE before switching — not whatever is active at commit time. (4) `dispatchCommand`'s early-return branch no longer masks a force-committed stroke's effect on `contentChanged`/`contentRevision`/`layerRevisions` — the force-commit's `dirty`/`changed` outcome now flows through the SAME "changed" path every other command already uses, instead of a special-cased early return. (5) `region.clear` clamps its rect to the canvas before writing (one `writeRect` call against a zero-filled patch) instead of looping over an unclamped rect and allocating a `{x,y,color}` object per pixel.

- **B1 (closed) — the slice routes through `PixelCore`.** `core.slice.ts`'s closure-held `core` is now a `PixelCore` instance from `resolveCore()` (`lib/core/core-config.ts`), not a raw `CoreState`. `dispatch`/`undo`/`redo`/`exportDocument`/`importDocument` call only `PixelCore`'s interface methods — never the TS-internal `dispatchCommand`/`createCoreState` functions. Swapping `resolveCore()`'s implementation for a future `WasmPixelCore` needs no change in this file.

- **B2 (closed) — `layerRevisions` crosses the boundary as part of `DispatchResult`.** `commands.ts`'s `DispatchResult` gained `layerRevisions: Readonly<Record<LayerId, number>>`, populated by `buildResult` from the core's internal state. `core.slice.ts` reads it off `result.layerRevisions`, never off `core`'s TS-internal state directly — closing the gap B1 would otherwise have reopened (a `PixelCore`-typed `core` variable has no `.layerRevisions` property to accidentally reach for in the first place now).

- **B3/B4 (deferred, documented) — NOT implemented this pass.** Both are real architecture changes whose blast radius is categorically larger than B1/B2 or the five bug fixes above, and rushing either one alongside a judgment-day bug-fix pass is the kind of shortcut this project explicitly avoids:
  - **B3** ("`snapshot()` becomes metadata-only; pixels cross the boundary ONLY via `readLayer`, and the store keeps a pixel cache refreshed by revision") would require `AnimationFrame`/`Layer`/`Timeline` to stop carrying pixel buffers everywhere they're read today. Critically, onion-skin rendering (`SpriteLayers.tsx`'s `OnionLayerImage`) reads OTHER frames' layers directly off `state.timeline.frames[...]`, not just the current frame — so a revision-driven pixel cache would have to cover every layer in the WHOLE document (keyed globally by layer id, which is safe since paste/add always mint fresh ids — see `ts-core.ts`'s `serializedFrameToFrame`), not just the current frame's layers, to keep every existing consumer working unchanged. That's a correct design (sketched here for the next pass), but implementing and verifying it safely (without an onion-skin regression) needs its own dedicated pass, not a slice of this one.
  - **B4** ("the core generates ids itself from a seedable `setIdSeed(prefix)` + internal counter, no JS callback across the boundary") would break every existing test that injects a deterministic `idGenerator` function to get reproducible ids — `ts-core.test.ts`, both prior judgment-day suites, `pixel-core.contract.test.ts`, and this round's own new tests all do this. The function-based `idGenerator` callback stays for now; swapping it for a seed+counter is a mechanical but wide-reaching rewrite (every `nextId(state)` call site needs to know whether it's minting a frame or a layer id) best done as its own pass with its own test-suite-wide update, not mixed into a bug-fix pass whose own regression tests also lean on the current mechanism.
  - Both are tracked as the recommended next pass before phase 3 (same "documented deviation, scope-contained" pattern as 2e.4/2c.4 above — not silently dropped).

- **Pixel cache contract (for B3's eventual implementation, documented now so phase 4+ isn't surprised by it)**: once `PixelCore.snapshot()` is metadata-only, `core.slice.ts` keeps a `Record<layerId, Uint8ClampedArray>` cache, refreshed by calling `readLayer(frameId, layerId)` — and COPYING the result out immediately, since `readLayer`'s view is only valid until the next `dispatch` (design D7) — for every layer whose entry in `DispatchResult.layerRevisions` changed since the last refresh, plus every layer on `importDocument`/`doc.replace`. `state.layers`/`state.timeline.frames[*].layers` are rebuilt from `snapshot()`'s metadata plus this cache every time, so every existing consumer that reads `layer.pixels` off the store keeps working unchanged. This is exactly how a future `WasmCore`'s `readLayer` (a view into Wasm linear memory, per D7) will work too.

### Phase 5f (fix-agent pass — two blind judges found real bugs/gaps in phase 4f/5; newest, read first)

- **Scanline span fill REPLACES the per-pixel stack algorithm (both Rust and the TS reference kernel).** `packages/core/src/flood_fill.rs` and `packages/core/src-ts/ts-core.ts`'s `tsKernels.floodFill` were both rewritten from "one stack entry per PIXEL" to "one stack entry per contiguous horizontal RUN" — `fill_span_row`/`fillSpanRow` expands left/right from a seed column and fills the whole run in one tight loop, cutting stack push/pop traffic from `O(w*h)` toward `O(h)` for a large open fill. External contract UNCHANGED (same dirty rect, same filled pixels, same 4-connectivity, same no-op cases) — verified against the ORIGINAL, never-touched `apps/editor/src/lib/flood-fill.ts` oracle (5,000-case randomized parity test, `flood-fill.oracle-parity.test.ts`) and against each other (`packages/core`'s existing 126-case fuzz suite + parity suite, unchanged, all still pass). Root motivation, MEASURED not guessed: the prior handoff's "chase the FFI whole-buffer copy" guess was wrong — isolated at ~1.6% of total time — the real cost was `O(w*h)` per-pixel compute. See `LEARNING.md` §13-16 for the full mechanism, including the counterintuitive result that this rewrite NARROWED the Wasm/TS ratio (both got faster, TS proportionally more so) even though it made Wasm itself substantially faster in absolute terms.
- **`opt-level` switched from `"z"` to `3`.** Verified (not assumed) smaller gzip on this crate's current size (10,273 vs 11,833 bytes, same scanline source) — see `LEARNING.md` §16 for why "optimize for size" isn't always smaller once `lto`/`codegen-units=1` already dominate dead-code elimination at a small crate's scale. Re-measure if a later phase grows this crate substantially.
- **Boundary number validation DECISION.** `packages/core/src-ts/ts-core.ts`'s `extractRect`/`writeRect`/`diffRect` and `wasm-core.ts`'s `makeWasmKernels` wrapper both gained a shared `isValidU32(n)` guard (`Number.isInteger(n) && n >= 0 && n <= 0xffffffff`), applied to every `w`/`h`/`rx`/`ry`/`rw`/`rh` argument BEFORE any further arithmetic or a Wasm call. Root cause closed: a plain `rx < 0`/`rx + rw > w`-style bounds check is silently `false` for `NaN` on either side, letting a NaN/fractional rect argument fall through and compute a NaN/fractional buffer index in TS, while wasm-bindgen's own JS->Wasm `u32` coercion separately TRUNCATES/WRAPS the same invalid inputs (`ToUint32`) rather than rejecting them — reaching Rust as a different, "valid-looking" number. DECISION: validate and reject on the TS facade for BOTH implementations, so wasm-bindgen's coercion is never reached for an invalid input in the first place — the Rust domain itself (`crate::pixels`) is unchanged by this decision (it already rejects every `u32` value it CAN receive that doesn't fit the buffer; the gap was JS values that shouldn't have reached a `u32` parameter as a "valid-looking" one to begin with).
- **`build-wasm.mjs` reproducibility hardening.** Also remaps `$CARGO_HOME` and `$RUSTUP_HOME` (previously only the crate's own source directory), so a future dependency's `.rs` sources won't reintroduce W1's cross-OS drift-check false positive. A post-build scan now FAILS the build (`process.exit(1)`) if any host-specific absolute path or backslash-style `.rs` path remains in the compiled `.wasm` — fail-closed instead of trusting the remap/substitution silently worked.
- **Dirty-pair cache: `evicted` always wins over `dirty` (closes a phase-4f gap, same root fix family).** `core.slice.ts`'s refresh loop now drops any `dirty` pair that also appears in `evicted` BEFORE calling `refreshLayer` on it. Root cause: a command that force-commits an open stroke AND deletes that exact `(frameId, layerId)` pair in the SAME dispatch (`layer.remove`/`frame.remove`/`doc.replace`) reports that pair in both lists — the force-commit's `dirty` entry and the delete's `evicted` entry — and the slice used to try refreshing it anyway, which `readLayer` correctly rejects (a gone frame/layer returns a 0-byte view) but the rejection path then fell back to an expensive, unnecessary full-document `refreshAllLayers` sweep, every time, for a case where nothing was actually wrong.
- **`setIdSeed` through `importDocument` — lazy minter (CRITICAL, closes a phase-4f W4a gap the verify report found).** `ts-core.ts`'s `payloadToDoc` used to construct its one-shot id minter (`makeLocalIdMinter`, which consumes-and-nulls the module-level `idSeedOverride`) UNCONDITIONALLY, even for a payload with no corrupted layers and no duplicate ids — the overwhelmingly common case. Since `TsPixelCore.importDocument` evaluates `createCoreState(payloadToDoc(doc))` left-to-right, this silently burned `setIdSeed`'s override before `createCoreState` (the function the override is DOCUMENTED to configure) ever ran, so the resulting core always minted ids under a fresh random prefix instead of the requested seed. Fixed: the minter is now LAZY (`let minter: ... | null = null; const getMinter = () => (minter ??= makeLocalIdMinter())`) — constructed, and only THEN consumes the override, the first time a payload actually needs a fallback layer or duplicate-id repair. The regression test for this exact scenario (`ts-core.ids-and-validation.test.ts`) passed BEFORE this fix too, but for the wrong reason (a random prefix trivially avoids colliding with a known seed's ids) — it now asserts the core's actual seed directly, which the pre-fix code could not have passed.
- **`core-config.ts`'s "wasm" fallback log, corrected and de-duplicated.** The old message ("no Wasm implementation exists yet") was accurate about `PixelCore` (the document/history boundary this file resolves, still TS-only until phase 7) but read as a claim about the whole `@pixelforge/core` package — false since phase 5, where `PixelKernels` (flood-fill, etc.) already runs on Wasm independently of this flag. Reworded to name both facts explicitly, and now logs at most once per session (was: once per `resolveCore()` call, i.e. every `ensureCore()`/`importDocument()`).
- **Bench pipeline determinism.** Root `package.json`'s `bench` script changed from `pnpm -r bench` to `pnpm -r --workspace-concurrency=1 bench`, serializing `packages/core`'s and `apps/editor`'s bench runs — removes the CPU/scheduling contention a prior verify report traced an intermittent dropped-benchmark-group flake to (`packages/core`'s own aggregated `core-results.json` losing a bench file's groups under concurrent execution). Proven with 3 consecutive clean `pnpm run bench && pnpm run check-bench` runs from the repo root.

### Phase 4f (fix-agent pass — judgment-day found real bugs in phase 4; supersedes the pixel-cache contract below where noted)

- **Dirty-pair cache-refresh contract (REPLACES the "refresh rule" in the Pixel cache contract section below).** `DispatchResult.dirty` is now `ReadonlyArray<{ frameId, layerId, rect }>` — every entry carries its OWN frame id, never implied by "whatever's current after this dispatch". `DispatchResult` also gained `evicted: ReadonlyArray<{ frameId, layerId }>` for layers/frames a command just removed. `core.slice.ts`'s pixel cache refresh is now driven ENTIRELY by these two lists (`evictLayers(result.evicted)` then `refreshLayer` for each `result.dirty` pair) — no more `STRUCTURAL_REFRESH_COMMANDS` command-type special-casing, no more "assume the post-dispatch current frame" guess. Root cause this closes: a command that both (a) force-commits an open stroke bound to the frame that was current BEFORE it runs, and (b) moves "current" to a DIFFERENT frame in the SAME dispatch (`frame.add` while a stroke is open is the simplest repro) used to report that stroke's dirty layer id with no frame context, and the slice guessed the WRONG (post-dispatch) frame — either aliasing the wrong frame's bytes onto that layer id, or caching a 0-byte miss if the two frames don't happen to share it. `frame.select`'s own case had the identical latent bug (discarded its force-commit's dirty rect entirely) despite never having been flagged before this pass. `readLayer` returning the wrong byte length (`!== w*h*4`) is now an explicit reject at the cache layer: `console.error`, keep the previous cache entry, fall back to a full `refreshAllLayers` sweep for that one dispatch — never cached as-is.
- **Undo/redo refreshes precisely, not a full sweep (closes a cost concern noted but not fixed in phase 4.0a).** `dirtyAndEvictedOf(entry, direction)` computes exact dirty/evicted pairs for EVERY `HistoryEntry` kind — `patch` (the patched layer/frame), `layer.add`/`layer.remove`/`frame.add`/`frame.remove`/`frame.paste` (the added/removed layer(s)/frame(s), direction-aware: an "add" kind's `'after'` direction is dirty, `'before'` is evicted, and vice versa for a "remove" kind), and `doc.replace` (the one case still touching every layer of every frame — a whole-document swap has no smaller representation, exactly as `entryBytes`' byte-budget accounting already treats it). Forward dispatch of `frame.add`/`layer.add`/`frame.paste`/`doc.replace` ALSO now reports explicit dirty pairs for their newly-created layers (previously relied on an implicit "bump all current-frame layers when dirty is empty" fallback in the `dispatchCommand` wrapper, which silently stopped working the moment `dirty` was non-empty for an unrelated reason — exactly C1's scenario); `frame.remove`/`layer.remove` report `evicted` pairs for the cache to drop.
- **Rust/TS boundary validation rules (hardens D6's "no serde, flat methods" surface against untrusted input).** Every function in `packages/core/src/pixels/mod.rs` now validates the buffer's length against `w*h*CHANNELS` (`valid_buffer`, via a `checked_mul`-based `buffer_len`) before touching it at all, and every rect/coordinate bounds computation uses `checked_add`/`checked_mul` (`index`) instead of plain `u32` arithmetic. This is NOT optional hardening gated by the release profile's `overflow-checks` flag — a JS caller passing a negative number for a `u32` parameter gets it silently coerced to a huge value by wasm-bindgen's generated glue (confirmed empirically: no throw), and plain arithmetic on that huge value WRAPS back into a small, bounds-check-passing number in a release build, after which the index computation wraps too, landing a write at the wrong memory location instead of being rejected. The TS parity reference (`packages/core/src-ts/ts-core.ts`) mirrors this with an explicit `rx<0||ry<0` check (JS numbers don't wrap the way `u32` does, so the equivalent fix is a direct sign check) plus the same buffer-length validation. `apps/editor/src/lib/pixel-buffer.ts`'s `extractRect`/`writeRect` get the same defensive hardening (not part of the formal parity gate, but the same bug class — "if shared", per the fix-agent's brief).
- **Reproducible `pkg/` across OS (closes a gap D9 assumed but never verified).** D9 says "CI rebuilds and diffs" `pkg/` but never addressed what happens when the committed `pkg/` was built on a DIFFERENT OS than CI — confirmed via a binary scan that it matters: `rustc`'s `file!()` macro (used by a bounds-check panic location the compiler couldn't fully optimize away) embeds this crate's source paths relative to the crate root, joined with the HOST'S NATIVE separator — `src\pixels\mod.rs` built on Windows, `src/pixels/mod.rs` on Linux CI, a byte-different `.wasm` for identical source. `--remap-path-prefix` (now set via `RUSTFLAGS` in `scripts/build-wasm.mjs`, which wraps `wasm-pack build`) only rewrites an ABSOLUTE path prefix and does not touch this (Cargo records the path relative to begin with); Cargo's purpose-built fix (`profile.trim-paths`) is still unstable even on this pinned stable toolchain. The actual fix: a narrow, deterministic POST-BUILD step in `build-wasm.mjs` that replaces ONLY the exact backslash form of each known `src/**/*.rs` path with its forward-slash form, as a same-length in-place byte substitution in the compiled `.wasm` (both separators are a single ASCII byte, so no length-prefixed section elsewhere in the binary is invalidated) — scoped to known source file paths, never a blind global `\`->`/` replace (which would corrupt unrelated opcode/LEB128 bytes that happen to equal that byte value elsewhere in the binary). Verified: two consecutive builds are byte-identical (reproducibility holds); a binary scan after the fix finds zero backslash/host-path matches. CI's drift check also now runs `git status --porcelain packages/core/pkg` (catches a NEW untracked generated file), not just `git diff --exit-code` (which only catches changes to files git already tracks).
- **Batched pixel-writing kernel, public facade narrowed (T1).** `PixelKernels` dropped `getPixel`/`putPixel`; added `putPoints(data, w, h, points, rgba)` (Rust `pixels::put_points`/`bindings::put_points`, mirrored in both TS kernel implementations). The per-pixel Rust functions stay in the domain module and its own `cargo test`s (useful building blocks, still wasm-bindgen-exported for anything that needs single-pixel Rust-side access), but `apps/editor`'s one real consumption path can no longer reach for a per-call shape the crate's own bench already proved costs ~1480x more than TS at that granularity.
- **Bench gate on a real batch operation, not a meaningless per-call ratio (W7).** The old `put_pixel x2000` gate budgeted 2500x against a number that was never a signal anyone could act on (the facade didn't even offer a batched alternative to compare against). Replaced with a gate on `putPoints` writing the SAME 2000 points in ONE call (measured ~1.2-1.3x, budget 2.0x) — the per-call shape still runs as an informative, non-gated bench row. `scripts/check-bench.ts` also now fails closed: a thresholds.json entry with no matching bench group, a missing ts/wasm row, or zero checked cases all `process.exit(1)` instead of warning and passing.

### Phase 4.0a/4.0b (B3/B4 closed — deferred blockers from Phase 2f, done before the Rust scaffold)

Phase 2f deferred B3 and B4 as documented, scope-contained deviations (see that section below). Both are closed now, before `packages/core`'s Rust crate lands, so the Wasm boundary design doesn't have to carry a known gap into phase 5+.

- **B3 — `PixelCore.snapshot()` is metadata-only.** `pixel-core.ts` adds `LayerMeta` (`Omit<Layer, 'pixels'>`), `FrameMeta` (`AnimationFrame` with `layers: LayerMeta[]`) and `DocMetaSnapshot` (`DocSnapshot`'s shape with every layer's `pixels` stripped), plus `toMetaSnapshot(doc): DocMetaSnapshot`. `PixelCore.snapshot()`'s return type changes from the internal, pixel-carrying `DocSnapshot` to `DocMetaSnapshot`; `TsPixelCore.snapshot()` now returns `toMetaSnapshot(this.state.doc)`. `ts-core.ts`'s internal engine (`CoreState.doc`, `currentLayers`, `currentActiveLayerId`, `dispatchCommand`) is **unchanged** — it still operates on real `Layer[]` with `pixels` inline; only the PUBLIC boundary narrows.
  - **Pixel cache, `stores/slices/core.slice.ts`**: a closure-scoped `Map<layerId, Uint8ClampedArray>`, keyed GLOBALLY by layer id (safe — `frame.paste`/`doc.replace` always mint fresh ids, never reuse one still live elsewhere in the document). `ensureCore()` warms it directly from the zustand state it bootstraps `core` from (no `readLayer` round-trip needed — those `Layer.pixels` objects are already in hand). After every dispatch that changes the document: for `doc.replace`/`frame.paste`/`undo`/`redo` (which can restore or introduce MULTIPLE frames' worth of layers at once — e.g. undoing a multi-frame paste only makes the FIRST pasted frame "current", but every pasted frame minted a brand-new, never-cached layer id), the cache does a full `refreshAllLayers` sweep; every other command diffs `DispatchResult.layerRevisions` against the last-seen map and calls `readLayer` only for the layer ids whose revision actually changed (always the CURRENT frame — every pixel-mutating command operates on `currentLayers(state.doc)`, so this is sufficient without a full sweep). `readLayer`'s view is COPIED immediately (`new Uint8ClampedArray(view)`, design D7: valid only until the next dispatch). `buildTimeline`/`buildLayer` then reconstruct the FULL `Timeline` (every frame, every layer) from the metadata snapshot plus this cache on every `result.changed` dispatch — the shape `state.layers`/`state.timeline.frames[*].layers` expose to the rest of the app is byte-identical to before this change, so SpriteLayers, onion skin, the eyedropper, selection/clipboard, export and persistence all keep reading `layer.pixels` off the store with zero call-site changes.
  - **Documented tradeoff**: rebuilding `Timeline` from metadata+cache is O(frames × layers) small-object allocations per content-changing dispatch, versus the previous O(1) reference passthrough (the engine's `DocSnapshot.timeline` was handed straight to zustand). Measured cost is not on the hot path the bench suite guards (full-repaint/flood-fill benches unaffected — see baseline-bench.md); acceptable for a typical document (tens of frames, a handful of layers each).
- **B4 — core-owned seedable ids, no JS callback at the boundary.** `CoreState.idGenerator: () => string` is replaced by `idSeed: string` (captured once at `createCoreState` time) plus two mutable nonce objects, `frameIdCounter`/`layerIdCounter: { value: number }`, held BY REFERENCE inside `CoreState` — spreading state (`withState`, `{...prev}`) copies the reference, so the counter survives every state transition (including undo/redo) without needing to be threaded through as an immutable patch. New ids are `${idSeed}-f${n}` (frames) and `${idSeed}-l${n}` (layers) — every former `nextId(state)` call site now calls `nextFrameId`/`nextLayerId` explicitly, so the core always knows which kind of id it's minting. `setIdSeed(prefix)` (exported from `ts-core.ts`) sets a module-level override used by every SUBSEQENTLY-created `CoreState`; without it, each `createCoreState` call picks a fresh `crypto.randomUUID().slice(0,8)` prefix ("default random prefix per session" — per-core-instance, not a single page-wide constant, specifically so re-importing the same stored draft twice in one page session can never collide with ids the draft already contains). `PixelCore.setIdGenerator` is removed from the interface entirely — a future Rust/wasm-bindgen core's equivalent is a plain `set_id_seed(prefix: &str)` export, no closure, no callback crossing the boundary. Parity tests that need two independently-constructed cores to mint the SAME id sequence call `setIdSeed(sameSeed)` before constructing each one (see `pixel-core.contract.test.ts`).

### Phase 2e revision (Wasm readiness of the core boundary — supersedes command shapes above)

Phase 2d's last line flagged this as the explicitly deferred next batch: making the TS core's boundary exactly the shape a Rust/wasm-bindgen core will have, so phases 4–7 swap the implementation without touching the UI. Done this round; `tasks.md`'s Phase 2e has the full list.

- **`syncCore` removed.** `core.slice.ts` no longer re-reads `canvasWidth`/`canvasHeight`/`timeline` from zustand state before every dispatch. The closure-held `core` bootstraps exactly ONCE, lazily (`ensureCore`), from whatever the store's initial state is; from then on `core` is the sole writer and zustand's document fields are a strictly one-way, read-only derived cache. `importDocument` is the one path that rebuilds `core` from scratch. Tests seed the document through `importDocument` (`lib/core/test-helpers.ts`'s `timelineToDocumentPayload`), not raw `setState`.
- **Explicit `DispatchResult`.** `{ changed, contentChanged, historyChanged, canUndo, canRedo, strokeOpen, revision, contentRevision, dirty }` — every field the store (or any future consumer) needs is computed by the core itself; the store no longer detects a committed stroke by comparing `core.history !== prev.history` object identity (`historyChanged` replaces it; it can be `true` even when `changed` is `false` — e.g. `stroke.begin` force-committing an already-open stroke).
- **Command payloads are serializable plain data — no live objects, no shared buffers.** `stroke.points`: `points: Int32Array` (interleaved x,y pairs) + `rgba: number` (packed u32, R highest byte / A lowest — `lib/core/color-codec.ts`'s `packRgba`/`unpackRgba`/`packPoints`); `layerId` dropped (redundant — a batch always targets the layer the open stroke already bound). `fill`: `rgba: number`. `frame.paste`: `SerializedFrame[]` (`lib/core/commands.ts`; ids optional — the core ALWAYS assigns fresh ones via its injectable `idGenerator`, never trusting a caller-supplied id, per the existing judgment-day round 2 "fresh ids on paste" decision); the core copies every pixel buffer it decodes. `selection.commit`: `{ layerId, at: Rect, pixels: Uint8ClampedArray (at.w*at.h*4) }` — a rect patch, not a whole-canvas buffer; transform baking stays in `stores/slices/selection.slice.ts` before dispatch (`diffRect`/`extractRect` compute the minimal changed rect). `doc.replace`: the core now `cloneBuffer`s each incoming frame's pixels instead of aliasing the caller's `PixelBuffer`.
- **`PixelCore` interface + `TsPixelCore`.** `lib/core/pixel-core.ts` introduces the stable interface a future `WasmCore` must satisfy (`dispatch`, `undo`, `redo`, `readLayer`, `snapshot`, `exportDocument`/`importDocument`, `setIdGenerator`, `canUndo`/`canRedo`), and `TsPixelCore` implements it as a thin OOP wrapper over the existing functional `dispatchCommand` engine. `lib/core/core-config.ts`'s `resolveCore()` reads `localStorage['pf:core']` → `process.env.NEXT_PUBLIC_PIXEL_CORE` → default `'ts'` (the app is still Next.js this phase; this is the one module phase 3's move to Vite needs to touch, swapping the env read for `import.meta.env.VITE_PIXEL_CORE`). `'wasm'` has no implementation yet — falls back to `'ts'` with `console.error`. Deviation (documented, scope-contained): `core.slice.ts` keeps calling the functional engine directly rather than routing through a `PixelCore`/`TsPixelCore` instance — adding that indirection to the already-stabilized zustand dispatch seam is deferred to phase 3, when `packages/core` actually splits out.
- **Boundary validation.** Every command that takes an id, index or rect now no-ops (`changed:false`) on an invalid one instead of trusting it — new this round: `selection.commit`'s `at` rect (out-of-range, non-positive, or a `pixels` byte length mismatch), `timeline.setFrameSelection`'s indices (filtered to the valid range). Everything else (`layer.setActive`, `frame.select`, `frame.remove`, `layer.remove`/`reorder`/`meta`, `frame.paste`'s clamped `at`) was already boundary-validated as of phase 2c/2d. None of these throw — a future Wasm core never traps on a bad id.
- **Core contract test suite.** `lib/core/pixel-core.contract.test.ts`, `describe.each` over implementations (only `'ts'` today) — dispatch/undo/redo/export/import round-trips with a deterministic injectable id generator. This is the future TS↔Wasm parity gate (phase 4+ adds a `'wasm'` row to the same table).
- **Rendering** already reads pixels via the `layers`/`layerRevisions` derived cache keyed by the per-layer revision counter (phase 2d, finding 1) — no component depends on buffer identity; this phase did not need to change any render call site.

### Phase 2d revision (judgment-day round 2 — supersedes/extends phase 2c above)

A second round of blind judge review found phase 2c's "every document mutation is undoable" correct in spirit but incomplete in two ways, plus three unrelated bugs. All fixed this round; `tasks.md`'s Phase 2d has the full list and test references.

- **Structural history memory (closes the phase 2c deviation above).** `lib/core/history.ts`'s generic `'structural'` kind (a whole-timeline before/after snapshot for EVERY structural op, however trivial) is replaced with one small record PER command: `layer.add`/`layer.remove` carry only the one `Layer`; `layer.meta` carries only before/after scalar metadata (no pixels); `layer.reorder` carries only `from`/`to` + the moved layer id; `frame.add`/`frame.remove` carry only the one `AnimationFrame`; `frame.paste` carries only the pasted frames. `doc.replace` is the one deliberate, documented exception — a whole-document swap genuinely has no smaller representation, so it keeps the full before/after `StructuralDocSnapshot`, still counted toward `pushEntry`'s byte budget like any other entry (never given a silent exemption). A visibility toggle on a 16-frame/4-layer/384px document now costs under 1KB, versus the whole document (twice) before this change.
- **Undo/redo focus (DECISION, Aseprite-style).** Undo/redo FOCUSES the frame/layer the applied history entry itself affected — if it still exists — falling back to the user's CURRENT selection if that is still valid, and only then to the nearest valid index. It never restores a stale selection recorded at the entry's push time, and it still never touches `fps`/`loop`/`isPlaying` (unchanged from phase 2c). Concretely: undoing a stroke re-selects the layer that stroke was drawn on, even if the user switched to a different layer afterward; undoing a `layer.add` re-selects the frame it was added to, even if the user navigated to a different frame afterward. This is a conscious choice to prioritize "show me what just changed" over "don't disturb what I was looking at" — the opposite choice is defensible, but Aseprite (the reference UX for this kind of editor) makes the same call, and leaving undo's destination undefined/inconsistent across entry kinds was itself a bug source.
- **Mid-stroke document-changing commands.** EVERY command that mutates the document (`frame.add/remove/paste`, `doc.replace`, `layer.add/remove/meta/reorder`, `region.clear`, `selection.commit`, `fill`) now force-commits any open stroke first, via a single guard in `dispatchCommand`'s wrapper (a `STROKE_COMMIT_COMMANDS` set checked once, before the big command switch) rather than scattered per-case calls. Previously only `stroke.begin`/`undo`/`redo`/`frame.select` did this — `fill` and the newly-undoable structural commands did not, so e.g. a bucket-fill dispatched mid-drag silently dropped or corrupted the in-progress stroke.
- **Autosave trigger split from the render/view trigger.** `CoreState.revision` (bumps on every dispatch, content or view — the render/UI-update signal) and a new `CoreState.contentRevision` (bumps ONLY when the document's persisted content actually changed) are now two different counters. `docRevision` — the field `document-persistence.controller.ts` watches to schedule an autosave — reads `contentRevision`. Previously it read the general-purpose `revision`, so autosave fired on every playback tick, frame navigation and fps/loop toggle too, not just real edits.
- **Render contract: revision counters, never buffer identity.** `stroke.points` mutates the SAME `stroke.working` buffer in place for an entire drag gesture (phase 2c's zero-clone perf fix) — `SpriteLayers.tsx` memoized its Konva image on `layer.pixels` identity, which never changes mid-gesture, so live strokes silently stopped rendering. Fixed at the contract level: a new per-layer `layerRevisions` counter on `CoreState` (bumped by the `dispatchCommand` wrapper from each dispatch's `dirty` rects, or — for structural ops — every current-frame layer) is threaded down to `SpriteLayerImage`/`OnionLayerImage` and used as the `useMemo` key instead of `layer.pixels`. This is also the contract a future Wasm core needs regardless — its buffers are views into linear memory, where JS object/buffer identity is meaningless, but a plain counter is cheap to expose from any backend.
- **Unique ids on paste, injectable id generator.** `frame.paste` now deep-copies every pasted frame with a FRESH frame id, fresh layer ids and freshly cloned pixel buffers, regardless of what the caller passed in — fixes real aliasing (pasting the same clipboard entry twice used to hand the core two frames sharing the same mutable layer/buffer objects). Ids are generated through `CoreState.idGenerator` (optional, defaults to `crypto.randomUUID`), so a later TS/Wasm parity suite (phase 7) can inject a deterministic sequence instead of comparing real UUIDs.
- **Validation + a persistence race.** `layer.setActive` with an unknown id and `frame.paste` with an out-of-range `at` are now no-ops/clamped instead of leaving `activeLayerId`/`currentFrameIndex` dangling. `document-persistence.controller.ts` gained an `isCancelled` checkpoint so a React-StrictMode-style cancelled-before-resolve start never runs migration/import, and `flush()` is a no-op when nothing is dirty.

#### Phase 2b note (superseded by phase 2c above — kept for history)

Every canvas mutation — undoable or not — goes through `dispatch(cmd)` (D3). At the time of phase 2b, two families existed: undoable (`stroke.begin/points/end`, `fill`, `frame.add`, `frame.remove`, `doc.replace`, `undo`, `redo`) and non-undoable (`layer.add`, `layer.remove`, `layer.meta`, `layer.reorder`, `layer.setActive`, `frame.select`, `frame.paste`, `selection.commit`, `region.clear`). Routing the non-undoable family through `dispatch` too (instead of a direct Zustand `set`) kept `timeline.frames[currentFrameIndex].layers` as the single mutable copy of a frame's pixels. Phase 2c above found that "non-undoable" split itself was a latent bug source and closed it.

  | { type: 'fill'; layerId: LayerId; x: number; y: number; rgba: number }
  | { type: 'layer.clear' | 'layer.remove'; layerId: LayerId }
  | { type: 'layer.add' } | { type: 'layer.reorder'; from: number; to: number }

}

Persistence port (phase 1: `src/app/editor/types/document.ts`; adapters in `src/app/editor/services/`):
```ts
export type DocumentId = string
export interface DocumentPayload {           // plain data: structured-clone safe
  schemaVersion: number                      // DOCUMENT_SCHEMA_VERSION, for future upgrades
  w: number; h: number; frameMs: number[]
  frames: { id: FrameId; layers: (LayerMeta & { id: LayerId; data: Uint8Array })[] }[]
}
export interface StoredDocument {
  id: DocumentId; revision: number; updatedAt: number // for future conflict handling (sync)
  payload: DocumentPayload
}
export interface DocumentRepository {        // async on purpose: a Supabase adapter is a drop-in
  load(id: DocumentId): Promise<StoredDocument | null>
  save(doc: StoredDocument): Promise<void>
  remove(id: DocumentId): Promise<void>
}
```
Adapters: `IndexedDbDocumentRepository` (DB `DOCUMENT_DB_NAME='pixelforge'`, store `drafts`, keyPath `id`) and `InMemoryDocumentRepository` (tests, and fallback when IndexedDB fails to open; the editor then shows a "drafts are not saved" notice). Phase 1 uses one draft id, `LOCAL_DRAFT_DOCUMENT_ID`. History is session-only and is never persisted.

`useDocumentPersistence.hook.ts` (mounted once in the editor shell): (1) open the repo, (2) run the legacy migration, (3) `load` and hydrate the store, then set `docStatus='ready'`, (4) only then start autosave: subscribe to document changes (phase 1: `layers`/`timeline` identity; phase 2+: `docRevision`), debounce `DOCUMENT_AUTOSAVE_DEBOUNCE_MS=800`, `revision+1`, `save`; flush on `visibilitychange→hidden`. Autosave must never run before restore finishes, or an empty doc overwrites the draft.

History entry (inside the core): `{ label, patches: { frame, layer, rect, before: Uint8Array, after: Uint8Array }[], structural?: { op, payload } }`. Undo writes `before`; redo writes `after`. During a stroke, `stroke.begin` copies the layer once into a temporary shadow buffer, and each point grows the bounding box. `stroke.end` then cuts `before` from the shadow and `after` from the live layer, drops the shadow, and pushes **one entry**. A 1-px stroke keeps about 8 bytes plus overhead (well under 1 KB). Budgets are new constants: `HISTORY_MAX_ENTRIES=50` and `HISTORY_MAX_BYTES=32*1024*1024`; the oldest entries are evicted until both limits hold. `frame.remove`, `layer.remove` and `doc.replace` keep the removed pixels in `structural.payload`.

The Rust surface stays at about 12 functions. It is shown for phase 4; phase 7 adds `Document`.
```rust
#[wasm_bindgen] pub fn flood_fill(data: &mut [u8], w: u32, h: u32, x: u32, y: u32, rgba: u32) -> Option<Box<[u32]>>
#[wasm_bindgen] pub struct Document { /* Vec<Layer{ id: u32, data: Vec<u8> }>, History */ }
// impl: new(w,h) · stroke_begin(layer) · stroke_points(&[i32], rgba) · stroke_end() · fill(..) · undo()/redo() -> bool
//       layer_ptr(frame, layer) -> *const u8 · layer_len(..) · revision() -> u32
```
How memory crosses the boundary (confirmed in the wasm-bindgen docs): a `&mut [u8]` argument is copied in and back out, which is fine for whole-buffer kernels at about 256 KB per call. A `Vec` return is always copied. So in phase 7, `WasmCore.readLayer` builds `new Uint8ClampedArray(memory.buffer, ptr, len)` again after **every** dispatch, because memory growth detaches the old views. The facade maps string ids to `u32` handles. Points are batched as `Int32Array`, so there are no per-pixel calls.

Flag: `resolveCore()` reads the localStorage override `PIXEL_CORE_OVERRIDE_KEY='pf:core'` (rollback without a redeploy), then `import.meta.env.VITE_PIXEL_CORE`, then defaults to `'ts'`. If Wasm init fails, it falls back to TS and logs with `console.error`.

## Data Flow

```
pointer → use*.hook ──dispatch(cmd)──→ PixelCore (TsCore | WasmCore)
                                         │ mutate in place, history patch
store.set({docRevision, doc: core.snapshot()}) ←── DispatchResult
renderer hook (selects docRevision) → core.readLayer() → per-layer offscreen
canvas (.data.set(view) → putImageData, only dirty rects) → drawImage(scale, globalAlpha)

docRevision ─debounce─→ useDocumentPersistence ─save(StoredDocument)─→ DocumentRepository
                                                                   (IndexedDB | InMemory; later Supabase)
editor mount → migrate legacy → load(id) → importDocument / store hydrate → docStatus='ready'
```
`putImageData` ignores `globalAlpha`, so each layer goes through an offscreen canvas and is drawn with `drawImage`. The shared `lib/buffer-to-canvas.ts` replaces the 2 `renderPixelsToCanvas` and 3 `getDrawOffset` copies.

### Phase 5 (Rust flood-fill — first compute-heavy kernel, first real editor wiring)

- **Rust surface.** `packages/core/src/flood_fill.rs`: `pub fn flood_fill(data: &mut [u8], w: u32, h: u32, x: u32, y: u32, rgba: u32) -> Option<(u32,u32,u32,u32)>` — a self-contained mirror of `apps/editor/src/lib/flood-fill.ts`'s algorithm (4-connected, stack-based `Vec<usize>` + a `visited` bool array, no recursion — see `LEARNING.md`'s Phase 5 section for why recursion is unsafe here specifically). Reuses `crate::pixels`' `valid_buffer`/`in_bounds`/`pack_rgba`/`unpack_rgba` rather than duplicating boundary validation; `bindings.rs`'s `flood_fill` wraps it to the same `Option<Box<[u32]>>` shape `diff_rect` already uses for a "maybe a rect" return.
- **`PixelKernels.floodFill` (D5).** Added to `packages/core/src-ts/types.ts`'s interface: `floodFill(data: Uint8Array, w, h, x, y, rgba): [number,number,number,number] | undefined` — operates IN PLACE, returns the dirty rect or `undefined` for a true no-op (invalid buffer, out-of-bounds seed, or a seed pixel already the fill color). `tsKernels.floodFill` (`src-ts/ts-core.ts`) is a from-scratch TS mirror (packages/core doesn't depend on `apps/editor`) using the IDENTICAL algorithm (visited array + stack) so the two TS implementations agree by construction. `makeWasmKernels`/`withRuntimeTrapFallback` wire the Wasm export and its runtime-trap fallback the same way every other kernel already does.
- **Boundary validation (D6 extended).** Same rules as phase 4f's pixel kernels: buffer length validated against `w*h*4` before anything else runs; an out-of-bounds seed or a same-color seed is a boundary no-op (`None`/`undefined`), never a panic/throw. 4-connectivity (no diagonal leak) confirmed to match the pre-existing TS editor behavior exactly (parity + fuzz tests assert this explicitly, including a diagonal-checkerboard case).
- **One optimization attempt, reverted (honest bench result).** Dropping the separate `visited` array (relying on "already-filled pixels can't match `target` anymore" as an implicit visited check) was tried to close the gap to the ≥3x proposal target. MEASURED as a net regression (ratio worsened from ~0.39-0.43 to ~0.6-0.7) — a `visited[p]` byte read is cheaper than the 4-byte color-check every duplicate stack entry would otherwise require, and 4-connectivity produces up to 4 duplicate entries per pixel. Reverted; `visited` stays in both the Rust and TS implementations. See `LEARNING.md`'s Phase 5 §12 and `baseline-bench.md`'s "Phase 5" section for the full numbers.
- **Result (open item, not silently hidden):** Wasm flood-fill is well within the <5ms absolute budget (~0.9-1.0ms mean on the dev machine, both the full-fill and maze/holes cases) but does NOT reach the proposal's ≥3x-faster-than-TS target — measured ~2.3x-2.6x, stable across repeated runs. `packages/core/bench/thresholds.json`'s `maxWasmToTsRatio` for both flood-fill gates (0.45, 0.48) is set just above the measured reality, not the aspirational 0.333 (3x) the proposal named — documented in a `_comment_flood_fill` key in that file, not silently loosened without a trace.
- **Editor wiring — the first phase that actually calls a Rust kernel from the live dispatch path.** `apps/editor/src/lib/core/kernels.ts` (new): bridges `dispatchCommand`'s SYNCHRONOUS requirement with `@pixelforge/core`'s ASYNC `resolveKernels()` — `getActiveKernels()` returns `tsKernels` immediately whenever `resolveCoreImpl()` (the SAME `pf:core` -> `VITE_PIXEL_CORE` -> `'ts'` override chain the rest of the core boundary uses) isn't `'wasm'`, starts an async Wasm load only when it is, and swaps the module-level "active" reference over once that settles (automatic TS fallback on load failure or a runtime trap is handled inside `resolveKernels()`/`withRuntimeTrapFallback` already — this module just reflects whichever implementation it decided). `lib/core/ts-core.ts`'s `fill` case now calls `getActiveKernels().floodFill(...)` instead of the old hardcoded `../flood-fill.ts` import; every bound/lock/no-op check around it (`isInBounds`, `layer.locked`, the kernel's own no-op) is UNCHANGED, so undo semantics (one dirty-rect patch entry, a `(frameId, layerId)` dirty pair) are identical regardless of which kernel ran. `apps/editor/src/lib/flood-fill.ts` (the original phase-1 TS implementation) is UNCHANGED and stays as the bench baseline reference — it is no longer on the production dispatch path, only its own tests/bench still call it directly.
- **`asKernelBuffer` (zero-copy type bridge).** `PixelKernels` operates on `Uint8Array` (packages/core's domain type); every pixel buffer in `apps/editor` is a `Uint8ClampedArray` (design D1). `new Uint8Array(data.buffer, data.byteOffset, data.byteLength)` reinterprets the SAME underlying `ArrayBuffer` with no copy — safe because flood fill only ever writes already-clamped 0-255 byte values, so the two views' clamping behavior never diverges.
- **Testing.** `packages/core/src-ts/pixel-parity.test.ts`: 9 new `floodFill` parity cases (full fill, wall/hole stop, diagonal-leak rejection, out-of-bounds seed, same-color no-op, transparent-vs-opaque, short-buffer rejection, maze-shape hole preservation, byte-for-byte ts/wasm agreement on a maze canvas). `packages/core/src-ts/flood-fill.fuzz.test.ts` (new): 100 deterministic-LCG-seeded random maze canvases, asserting ts and wasm agree byte-for-byte AND on the dirty rect every time, plus out-of-bounds/same-color-seed and adversarial-short-buffer cases. `apps/editor/src/lib/core/kernels.test.ts` (new): the sync/async bridge itself (default stays ts and never loads Wasm; a `'wasm'` override resolves and the flag can roll back immediately). `apps/editor/src/lib/core/ts-core.kernels-wiring.test.ts` (new): mocks `./kernels` with a fake `PixelKernels` whose `floodFill` writes a deliberately-wrong recognizable pattern, proving `dispatchCommand`'s `fill` case actually calls the resolved kernel and uses its output — not just that the default TS path still produces correct pixels (every pre-existing `fill`-dispatching test already covered that).
- **The `PixelCore` contract suite (`pixel-core.contract.test.ts`) is unchanged, deliberately.** That suite is parameterized over FULL `PixelCore` implementations (`describe.each`), and only `TsPixelCore` exists — a `WasmPixelCore` is phase 7's job (D5: "two seams," the stateful document seam lands last). Phase 5 only wires the STATELESS `PixelKernels` seam into `TsPixelCore`'s internal `fill` dispatch; there is no second `PixelCore` implementation yet for that suite to parameterize over. The ts/wasm KERNEL comparison lives in packages/core's own parity/fuzz suites instead (previous bullet).

## Migration / Rollout

- Phase 1 legacy migration (one-time, idempotent): if localStorage `sprite-editor-core` holds `layers`/`timeline`, convert each `RgbaColor[][]` with `rowsToBuffer`, build a `StoredDocument` (`revision: 1`), `save` it, and **only after the save resolves** copy the colors into `sprite-editor-prefs` and remove the legacy key. A failed save keeps the legacy key, so the next load retries. If a draft already exists in IndexedDB, the draft wins and the legacy key is removed.
- Phase 2: no data migration. The stored format stays `DocumentPayload`; only its producer changes.
- `supabase-project-sync` (future change): adds a Supabase adapter behind `DocumentRepository`; `revision`/`updatedAt` are the conflict inputs.
- Each phase is its own PR or tag.
- Phases 4–7: change the flag or the `pf:core` override to roll back.
- Gotcha: wasm-pack writes `pkg/.gitignore` containing `*`. `build:wasm` must delete it, or the committed `pkg/` silently goes empty.
